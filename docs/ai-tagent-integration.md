# AI-TAgent / Mattermost 集成设计

状态：设计基线，已增加可离线构建/测试的本地请求受理插件；不代表已经接通、部署或通过端到端验收。

## 0.2.6 进展：持久复核状态、终止取消与独立对账

独立收件箱新增授权前/执行前复核状态机；每次含重复请求均重新验证证明、来源
状态/到期/内容承诺及更高的主库确认版本，并在本地事务中核验动作权限、固定目标
和预期版本。状态与审计同事务写入，来源异常或旧版本失败关闭，在条件允许时持久
记录 blocked。`authorization_observed` / `execution_observed` 都只是历史观察，
不是审批、租约或执行令牌；没有可运行/完成状态和执行器，仍默认关闭。

新增独立本地鉴权的 Inspect/Cancel：按原 delivery key 查询有界操作历史，无需
旧证明仍有效或来源在线；按原操作 ID 对账未知提交结果。Cancel 是本地终止状态，
与并发复核通过行锁/版本一致处理，不能复活。映射 actor 仅是资源所有者，不能当
登录身份；真实本地调用者须另经可信身份上下文鉴权，现仅使用合成测试适配器。

源版本是本次 CAS 确认的全局 ledger revision，不是租户隔离计数或防数据库恢复
回滚的可信 epoch。负面测试仍确认最后来源读取之后的远端取消可留下历史观察，
不能据此执行。真实 claim/取消传播、执行幂等/栅栏、sender outbox、服务身份/TLS、
恢复 epoch 与实际 Octop 权限仍阻断接线，不承诺分布式绝对原子。

隔离 PG 15.20 已验证实际来源→落库→两阶段复核→取消阻断→本地取消，以及并发、
撤权/密钥轮换、审计回滚、提交回执丢失恢复、到期和超时。测试仍是 fake Mattermost
API/KV + 独立 PG，不是真双服务；SQL 使用超级用户，不证明最小权限或审计防篡改。
历史上限每行8个事件（保留取消位置）；128条留存上限不因取消/过期释放，满后停止
受理，仍无完成、清理或墓碑归档。DDL仅用于一次性测试，未提供实际升级迁移。

## 0.2.5 进展：实际来源适配器与隔离持久化链路

新增来源适配器实际调用插件权限检查及主库 CAS 确认，前后复核配置/权限；请求
身份来自可信固定绑定，不从 HTTP 头或客户端正文获取。只返回意向承诺哈希、状态
与到期时间，不返回 goal/proof。来源和收件箱默认关闭，只有隔离测试构造启用实例；
未新增运行时 HTTP、秘密供应、网络连接或执行入口。哈希不是认证令牌或加密，真实
服务认证及查询新鲜度/防重放仍需独立协议。

独立 PostgreSQL kernel 将唯一交接键、冲突指纹、稳定目标 ID、待授权状态和审计
同事务提交；不存 goal、原始 proof 或秘密。每次含重复请求均重新检查来源与接收方
事务内授权。提交错误保守返回 commit_unknown，禁止自动新建身份。真实隔离 PG
15.20 验证了命令→来源→落库、八进程唯一写入、重连重复识别、密钥轮换、撤权、
审计失败回滚、真实提交后模拟丢失确认、到期、128 留存上限和有界锁等待。

这不是 Octop schema migration；其真实授权事务适配器尚未交付，测试使用合成授权
表和 Mattermost API/KV fake。保留负面测试：来源确认后发生取消，仍可能留下待授权
行，因此不允许其驱动执行或声称完成实时撤销。持久记录没有清理/重置接口，满128
后失败关闭；生产留存、租户公平、来源 claim/取消传播、未知结果对账、sender outbox、
可信身份/TLS、执行器秘密隔离和真实端到端验收继续阻断接线。详见插件 README。

## 0.2.4 进展：来源过期、取消复核和跨语言向量

离线证明升级为 v2，签入来源回执的毫秒到期时间；签发和校验均禁止证明超过来源
到期，且仍最多 120 秒。v1 不再接受，不改变本地 ledger schema。签名不会因来源
取消而自动失效，因此新增离线 `VerifyWithSource`：强制逐次来源状态复核，拒绝
已取消、缺失、错误或内容/绑定/到期变化，并在复核后再次检查时间。测试使用真实
本地命令 fixture 先签后取消，验证纯签名仍有效而来源复核拒绝。未配置真实 reader。

来源新鲜读取仍不能消除读取后取消与接收事务之间的竞态；真实接线前必须实现来源
claim/取消及未知结果对账协议，或明确的待授权取消协议与执行前复核。当前结果不能
直接创建可执行任务，不能宣称零窗口撤销。实时 Octop 权限和服务信任仍需独立核验。

组织/员工来源 ID 保留旧配置的有效 UTF-8 原始字节（128 字节上限），不进行名称
猜测、slug、大小写或 Unicode 归一化。接收策略必须显式绑定稳定 Octop 组织、员工
和用户 ID，映射变化进入冲突指纹；尚未实现部署侧映射注册、版本和实时授权。

新增十个公开合成向量，由 Go 与 Python/OpenSSL 校验编码、Ed25519 签名及交接/
冲突哈希。此格式仍为明确约定的 Go JSON 编码而非跨语言 canonical 标准，Python
脚本不是生产接收端。base64 正文可解码而非加密；真实 TLS、日志/存储保护、唯一
交接键+指纹+待授权+审计事务、持久去重和业务幂等全部仍是接线门禁，未宣称完成。

## 产品边界与首个场景

AI-TAgent（Octop / 轻智能体系统）负责数字员工、目标规划、执行、审批、证据和审计；
Mattermost 负责真人与数字员工协作入口；AKB 负责授权知识归档；模型网关负责模型调用与费用。
先采用外部适配器和 Bot REST API，再考虑独立插件，不先修改 Mattermost 核心。

首个验收场景为“运维数字员工晨检”：真人提出目标 → Octop 规划允许列表内的只读检查 →
审批执行 → 保存结果及证据 → 主管验收 → 审批指定频道与摘要 → Bot 发布报告链接 →
独立授权后归档知识。聊天文本、外部素材和模型生成的指令都不能自行授予执行或外发权限。

## 身份与权限

- 真人使用自己的 Mattermost 用户；数字员工使用专属 Bot，不借用真人 token 或展示名称冒充真人。
- 建立受控绑定：Octop 组织、用户、数字员工、Mattermost 实例、team/channel、Bot user ID。
- 区分 `human_requested` 与 `scheduled`。记录实际发起人、数字员工、Bot、run、approval、目的地和报告摘要哈希。
  定时任务记录其授权来源，不捏造真人操作。
- Bot 默认最小权限，不授予系统管理员。每次提交、执行、审批、发送均重新校验相关权限；
  频道成员身份不自动等于 Octop Agent 访问权。
- 初期审批跳转 Octop，复用登录和权限链；后续交互按钮必须验证当前用户、审批版本和防重放条件。

## 接口和事件契约

建议独立连接记录保存固定服务地址、凭据引用与状态；绑定记录限定允许的频道。
凭据保存在服务端秘密存储，不进入通用可回显配置、日志、错误消息或浏览器响应。

外发采用持久化 outbox：以实例、run、报告版本、目的地和审批绑定幂等键，记录发送状态及远端 post ID。
网络超时且远端结果不明确时标记 `delivery_unknown`，先对账，不盲目重发。
报告、频道或绑定变化使原审批失效；撤权、Bot 禁用和凭据失效均应阻断。

后续插件通过显式 `/aitagent` 命令接收目标，并展示任务卡片/详情栏。
事件包含来源实例、事件 ID、可信用户与频道 ID、关联 run 和类型；入口认证和用户映射完成后才能进入任务系统。
过滤自身 Bot 消息，防止消息回环；重复、乱序和重放事件不得重复执行任务。
仅在 Mattermost 管理的插件 HTTP 入口信任其认证头，不信任公网请求伪造的同名头。

## 隐私与审计

只发布已经批准的最小摘要及受权限保护的链接，默认不复制原始内部响应、凭据或聊天历史。
频道权限与报告权限分别校验；知识归档是单独授权步骤，不因发布到频道而自动归档。
审计保留身份映射、操作模式、授权来源、内容哈希、目标、时间、run、审批和发送回执；
审计中避免存储秘密和不必要的正文。留存、撤销和删除策略在上线前明确。

## 0.1 本地协作入口

`server/cmd/aitagent-plugin/` 实现独立的 `/aitagent request <goal>` 和
`/aitagent status <receipt-id>` 插件入口，详见该目录 README。它默认关闭，限定
管理员配置的组织、数字员工、专属 Bot、团队、频道及真人受理白名单。每次请求和查询
重新检查真人/目标 Bot 状态、频道归属、成员关系及真人发帖权限。

插件使用 Mattermost 服务端命令 hook 的已认证账户身份，并将目标正文视为不可信数据。
受理记录分开保存真人、数字员工、Bot、来源、目标哈希和绑定，状态固定为
`awaiting_octop_authorization`。`user_requested` 仅表示非 Bot 账户提出目标，不证明真人正在键盘前操作
（用户会话/token 也可能被自动化使用），不声称由人实际执行。后续人工代操作与自动执行
必须另记每步实际操作者及授权来源。

本阶段只有本地 KV 受理和仅本人可见的回执，七天过期；组织/数字员工映射尚未向
Octop 验证，不授予其业务权限。相同命令 dispatch 原子去重，Bot 操作者拒绝，
不监听普通聊天或 Bot 消息。没有外发客户端、执行器、审批、调度或真实 Octop 队列。
新的命令提交会有新的服务端 trigger，不能据此声称已实现跨请求或永久幂等。

离线单元测试和插件包构建不替代真实实例安装、RPC/数据库及端到端验收；
本地受理不是 1.0 完成，也不代表 Octop 发布预览已经接通真实发送。

**命令输入与审计保留提示（0.1.1）**：不得在斜杠命令中输入密钥或敏感信息。
`api4/command.go` 在插件处理前将完整 `CommandArgs` 加入服务器审计记录；
`CommandArgs.Auditable()` 包含完整 command/goal，插件拒绝也不能撤回已捕获的内容。
七天仅是插件 KV 回执的过期规则，不约束服务器审计、收集器、导出或备份的保留。
内置审计文件目标默认 `max_age=0`、`max_backups=0`，不自动按年龄或份数清理旧文件。
插件 README 提供源码核实的配置边界、离线校验的独立示例及真实部署前的验证步骤；
自动补全、管理设置和所有命令响应均明确提示两套保留策略不同。

## 0.2 受理配额与并发边界

新增每用户（跨组织）4 次/滚动 60 秒、8 条未处理，每配置组织 16 次/60 秒、
32 条未处理，整个插件安装 32 次/60 秒、64 条未处理的限制。总保留回执（含取消墓碑）
上限 128 条，状态上限 2 MiB；每进程最多 4 个并发命令，每操作最多 8 次 CAS 尝试。
这些范围不跨不同 Mattermost 实例，也不证明管理员配置的组织 ID 已向 Octop 验证。

回执、未处理状态及速率历史共用一个非过期 KV 状态，单次数据库 CAS 一并提交。
源码确认写入在主库，读取可能来自副本；旧快照只能导致条件写失败或保守拒绝，不能
无条件覆盖新状态。增加 `/aitagent cancel <receipt-id>`，按现有身份/权限校验取消，
仅释放未处理配额，不退还速率、不立即删除去重墓碑。相同 dispatch 去重仍不等于
业务幂等或任务“恰好一次”。没有 Octop worker，不能把回执标为已执行或已交付。

七天在 0.2 明确为回执访问期限：过期条目在后续成功状态操作中惰性清理，插件停用、
无流量或存储故障时原文可能继续物理保留。整个状态不设置数据库 TTL，以免旧回执
到期时误删新预约。服务器审计、导出及备份仍独立保留。取消删除当前状态中的 goal，
但不撤回任何已产生的审计/备份副本。

`QuotaStorageReady` 与 `Enabled` 均默认关闭。前者是运维确认，不是自动就绪检测：
旧版写入必须在所有节点停止，旧回执生命周期需核实结束/完成治理，并核实主副本一致、
节点时钟同步后才可开启。不支持旧版滚动混跑、自动迁移或清零绕过配额；副本前缀检查
看不到旧 key 不能证明主库为空。无法核实时安全升级仍阻塞。向后跳钟拒绝操作；
任意向前跳钟无法由 KV API 判别，不能宣称任意时钟偏差下的真实时间速率保证。

离线测试覆盖共享 CAS、延迟副本、前/后提交故障、取消/过期释放及全部配额范围；
独立临时 PostgreSQL 测试只核实所复现 SQL 原语，不替代真实服务器/集群端到端验收。

## 0.2.1 查询、取消与过载保护

增加独立的进程内滚动 60 秒工作限流：每用户 request 4 次（重复 dispatch 也计数）、
status 6 次、cancel 4 次，三类合计 12 次；每进程所有用户合计 60 次。
这些限制不跨节点，重启会重置，不是集群全局查询/取消限流。原有数据库共享受理配额保留。
status 和重复 dispatch 仍通过整份 ledger CAS 确认主库状态，写放大问题仅被限制频率，
没有被宣称消除。

源码核实插件 API 是同步 `net/rpc.Call`，无逐次 context/deadline；SDK 传输错误可能
被记录后返回零值。新增两秒协作式工作预算、调用前后检查、CAS 指数退避与抖动，
但不能取消已经发出的 RPC，也不保证两秒返回。不会新建超时后遗留的后台 worker；
最多四个原调用占用槽位，进程满或发现逾期调用时新命令立即拒绝；迟到调用返回后
释放槽位并冷却 30 秒。永不返回的 RPC 仍依赖服务/传输恢复或受监督重启，是 1.0 阻断。

回执不可用可能来自副本滞后或传输故障，不能证明未落库；超时/未确认写提供原回执 ID，
不得据此自动创建新请求重发。新增标准 `ServeMetrics` hook，仅输出固定进程内计数和
逾期/并发指标，不访问 KV、不带用户/组织/正文标签，不开启监听器或绕过部署许可。
实际 metrics 路由和故障时可用性未验证。

旧版写入全部停用、主副本核验、时钟同步、128 条墓碑可能停接、惰性物理清理、
实际集群过载与业务幂等/Octop 交付等边界继续有效；`QuotaStorageReady` 不是自动安全迁移。

## 0.2.2 绑定范围预过滤与可用性边界

确认 0.2.1 在白名单/频道鉴权前消耗进程 60 次总预算，其他已认证账户在各自频道
发起的拒绝请求也可能占满预算，不能称为租户隔离。0.2.2 在激活及配置变更时加载
只用于拒绝的有界快照；白名单外、团队/频道不匹配的请求不触发 RPC、不消耗工作预算，
也不按来访账户新增缓存。通过预过滤不等于获准：仍逐请求重新加载配置并检查全部当前权限。

配置快照在刷新开始前失效；失败、重叠或过期刷新结果都不能恢复旧快照。每进程最多一个
同步配置加载，不创建后台刷新/排队 worker；重叠事件后保持关闭，需恢复后重新触发
受支持的配置刷新。该生命周期 RPC 也不可取消，真实集群配置事件一致性未验证。

负面测试明确保留：已在白名单、范围匹配的账户仍可因目标 Bot 被禁用等实时检查失败
消耗共享预算；恢复 Bot 后其他正常账户仍可能被限流。单个命令 RPC 逾期也会阻断
新工作，即使另三个槽位空闲。这是保护共享资源的全进程策略，不是租户公平性或隔离。
640 个并发范围外请求不触发配置 RPC/占用预算的缓解测试通过，不代表上述风险已消除。

1.0 仍要求在正确身份边界下设计并验证公平的服务端/入口资源预算、已知调用方滥用和
后台故障处置；默认关闭、未知写入对账、迁移核验、墓碑容量与审计/清理限制全部保留。
